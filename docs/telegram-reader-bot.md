# Интерактивный Telegram-бот читателей

Бот обрабатывает личные сообщения через Cloudflare Pages Function `/api/telegram-webhook`. Команды: `/start`, `/help`, `/catalog`, `/latest`, `/search [название]`. Название можно отправить отдельным сообщением. Все кнопки работают через inline keyboard; личные данные пользователя не выводятся в журналы. Группы и каналы не обрабатываются. Обычная отправка уведомлений о главах остаётся в GitHub Actions и использует прежнюю ветку журнала.

## Данные и границы публикации

Каталог берётся из `catalog.json` текущего развёрнутого сайта через Pages Assets, а не из `main`. Статические главы с датой в будущем исключаются. Для произведений с `serial: true` функция запрашивает главы с **публичным** ключом Supabase: RLS возвращает только открытые главы. Ключи другого формата отклоняются. Дата очередной главы сериала вычисляется по действующему серверному расписанию в `backend/serial-releases.sql`; в `/latest` попадают только главы, видимость которых подтвердил публичный запрос. Если источник недоступен или неполон, запрос завершается сообщением об ошибке, без показа непроверенного содержимого.

Постраничный каталог и результаты поиска показывают только произведения с опубликованными главами. Для художественных названий используется обычный текст Telegram, без HTML-интерпретации. Номера карточек в кнопках относятся к текущему каталогу: при его изменении старую кнопку следует открыть заново.

## Развёртывание (только после отдельного согласованного релиза)

1. Сначала объединить PR #127, затем этот зависимый PR; после squash-merge #127 при необходимости перебазировать ветку этого PR на актуальный `main`. Убедиться, что формат уведомлений и тесты PR #127 сохранены.
2. Применить `backend/telegram-bot-guard.sql` к **существующему** проекту Supabase в SQL Editor с административными правами. Миграция создаёт отдельную роль `telegram_bot_guard` без `LOGIN` и `BYPASSRLS`, предоставляет её только `authenticator`, ограничивает права двумя таблицами защиты и включает для неё RLS-политики. Функция работает с правами вызывающего (`security invoker`); `anon` и `authenticated` не имеют доступа к таблицам и функции. Миграция специально завершится ошибкой, если роль уже существует: повторное применение требует ревью, чтобы не унаследовать неизвестные полномочия. Проверить права и RLS в Supabase Advisors. Ничего не применять к production до ревью миграции.
3. В Cloudflare Pages → проект `hunmeng-novels` → Settings → Variables and Secrets задать для production:
   - `TELEGRAM_BOT_TOKEN` — существующий токен бота, **encrypted secret**.
   - `TELEGRAM_WEBHOOK_SECRET` — отдельное случайное значение из 32+ символов, состоящее только из букв ASCII, цифр, `_` и `-`, **encrypted secret**.
   - `TELEGRAM_HASH_SECRET` — независимое случайное значение минимум из 32 символов, **encrypted secret**, для HMAC пользовательского ID.
   - `SUPABASE_URL` — адрес проекта с SQL-миграцией.
   - `TELEGRAM_GUARD_JWT` — **encrypted secret**, подписанный проектом JWT с `role: telegram_bot_guard` и конечным `exp`. Это ограниченный токен роли, а не `service_role` и не ключ подписи. Выпускать его в защищённой среде по [инструкции Supabase](https://supabase.com/docs/guides/auth/signing-keys), например `supabase gen bearer-jwt --role telegram_bot_guard` с подходящим сроком действия и доверенным проектом ключом. Сначала проверить `supabase gen bearer-jwt --help` и конфигурацию ключа; не печатать токен в журнал, историю shell или переписку. Настроить напоминание и ротацию **до** `exp`: после истечения бот откажет в обработке с 503. Для выдачи или обновления JWT не хранить приватный ключ подписи в Cloudflare. Не менять подписывающие ключи проекта без отдельного согласования. Роль и работоспособность токена нужно подтвердить в тестовой среде до выпуска.
   - `PUBLIC_SUPABASE_URL` и `PUBLIC_SUPABASE_PUBLISHABLE_KEY` — адрес и публичный ключ (`sb_publishable_…`) того же проекта; ключ используется и как `apikey` для ограниченного RPC, и для проверки опубликованных глав по RLS. Никогда не подставлять сюда `service_role` или secret key. Подписанный JWT передаётся отдельно в `Authorization`.
4. Выпустить **одобренную** ревизию сайта штатным workflow Pages. Wrangler должен запускаться из корня репозитория, чтобы включить корневую директорию `functions/`; перед релизом проверить, что функция вошла в сборку. Секреты production и preview разделены. Публикация main автоматически не включается.
5. Только после проверки готовности endpoint зарегистрировать webhook через Telegram `setWebhook` на `https://hunmeng-novel.ru/api/telegram-webhook`, передав тот же `TELEGRAM_WEBHOOK_SECRET` как `secret_token` и `allowed_updates` = `["message", "callback_query"]`. Перед переключением проверить текущий webhook: у одного бота может быть только один, и `setWebhook` заменит его. Не использовать `drop_pending_updates`. Передавать токен и secret через защищённое окружение/менеджер секретов, а не через историю shell, URL в логах или переписку. После переключения проверить `getWebhookInfo` без раскрытия секрета, выполнить `/start`, поиск и переход к чтению в личном чате. Не публиковать тестовые сообщения в канал.
6. При откате сначала удалить/восстановить прежний webhook и лишь затем откатить Pages. Не трогать `telegram-notification-state` и не запускать повторно доставку глав. SQL-таблицы и их данные не удаляются автоматически.

## Обработка ошибок и хранение

Запросы к Telegram и Supabase ограничены тайм-аутом. До регистрации update недоступность БД возвращает 503; Telegram может повторить запрос. При неоднозначном тайм-ауте RPC запись могла сохраниться: повтор будет распознан как дубликат, и ответ пользователю может потеряться; пользователь может отправить запрос ещё раз. После успешной атомарной регистрации возвращается 200 даже при неоднозначной ошибке Telegram, чтобы избежать повторной отправки ответа; пользователь может заново нажать кнопку. Лимит — 12 запросов на пользователя в минуту, применяется в общей базе ко всем экземплярам. ID пользователя хранится только как HMAC-SHA-256; ключ HMAC находится в секретах Pages. ID обновлений и хеши хранятся до очистки после трёх дней; очистка выполняется периодически входящими запросами, поэтому при отсутствии трафика записи могут сохраняться дольше. Сообщения, токены и содержимое запросов не сохраняются в таблицах и не логируются кодом.

Поведение проверяется `node --test tests/telegram-bot.test.mjs tests/telegram-bot-guard.test.mjs tests/telegram-chapters.test.mjs tests/telegram-delivery-safety.test.mjs`. Тест SQL запускает изолированный локальный PostgreSQL и пропускается, если серверные утилиты отсутствуют. Все вызовы Telegram в этих тестах замоканы. Перед выпуском дополнительно проверить SQL параллельными вызовами и состояние журнала уведомлений.
