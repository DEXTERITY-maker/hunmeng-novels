# Координация публикаций Hunmeng

Этот документ описывает подготовленные локальные изменения. До их отдельного
согласования и применения действующие процессы GitHub и production не меняются.

## Аудит текущих путей

Проверено состояние `main` на 2 ноября 2026 года и определения в репозитории:

| Процесс | Триггер и состояние | Общий ресурс |
| --- | --- | --- |
| `pages-manual-draft.yml` | Ручной запуск из `main` с точным SHA или push с одной из явно перечисленных исторических тем коммита; последний запуск на `main` завершился успешно. | Cloudflare Pages |
| `import-public-domain.yml` | Ручной запуск из `main` или конкретная историческая тема коммита; при отсутствии новых книг публикация пропускается. | `main`, Cloudflare Pages |
| `publish-approved.yml` | Расписание и ручной запуск разрешают работу только при `HUNMENG_PUBLISH_ENABLED == 'true'`. На момент аудита переменной репозитория нет, последние запуски по расписанию пропущены. | `main`, статусы Supabase |
| `publish-historical-covers.yml` | Push в `main` с конкретным историческим префиксом сообщения коммита. | `main`, Cloudflare Pages |
| `publish-alice-historical-cover.yml` | Push в `main` с одним из двух конкретных исторических префиксов. | `main`, Cloudflare Pages |
| `check.yml`: `deploy-timeweb` | Постоянно отключён через `if: ${{ false }}`. | Устаревший путь развёртывания Timeweb |

Исторические префиксы по-прежнему являются условиями допуска: повторное
использование совпадающего сообщения может активировать соответствующий процесс.
Статус `active` в списке GitHub означает, что workflow не отключён; он не означает,
что его условие выполнено. GitHub также показывает исторические workflow, файлов
которых уже нет в текущей `main`. Telegram-уведомления пишут отдельный ref
`telegram-notification-state`, а не `main`, и не публикуют Pages.

## Очередь и проверка ревизии

У пяти действующих заданий публикации одна группа `hunmeng-pages-production` на уровне
job с `queue: max` и `cancel-in-progress: false`. Отключённый Timeweb
не участвует в очереди; перед его возможным включением потребуется отдельный аудит.
Сценарии с собственным коммитом проверяют SHA, записанный после
успешного `git push`; для остальных проверяется SHA исходного события. Непосредственно
перед развёртыванием `verify-main-revision.mjs` проверяет точный локальный HEAD,
отсутствие незафиксированных файлов и актуальный `refs/heads/main` через GitHub API.
Для Pages проверка выполняется и перед вызовом Wrangler Action, и в его
`preCommands` после возможной установки Wrangler. Настройка `npm_config_save: false`
не даёт установке менять `package.json` и `package-lock.json`. См. [порядок шагов
Wrangler Action](https://github.com/cloudflare/wrangler-action/blob/953926a2e2182532811c01a25e53647d93bf07c0/src/wranglerAction.ts) (версия v4 закреплена по SHA; ненулевой код `preCommands` прерывает Action до
команды deploy)
и [настройку npm `save`](https://docs.npmjs.com/cli/v11/using-npm/config/#save).
Для Pages тот же SHA передаётся Wrangler как метаданные
[`--commit-hash`](https://developers.cloudflare.com/workers/wrangler/commands/pages/#pages-deploy).
Ошибка проверки останавливает следующий шаг; автоматического повторного выпуска нет.
Для повторной проверки существующий токен GitHub передаётся в окружение Wrangler
Action и его дочерних процессов; выданные ему права не расширяются.

Сценарии импорта и обложек получают checkout SHA события. Если `main` продвинулась
пока задание ожидало очередь, обычный non-fast-forward push отклонит устаревший
коммит. Проверки разрешений, лицензий, триггеры и права токенов не расширяются.

На GitHub.com очередь поддерживает до 100 ожидающих заданий; последующие при
заполненной очереди отменяются. Порядок определяется временем входа в очередь,
а не обязательно временем события. `queue: max` несовместим с
`cancel-in-progress: true`; поддержку в других установках GitHub Enterprise
Server необходимо проверить отдельно. Источники: [документация GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency),
[объявление GitHub](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/).

## Остаточные риски и восстановление

- Блокировка действует только для заданий с этой группой в том же репозитории.
  Прямые push, сторонние автоматизации, возможная Git-интеграция Cloudflare и
  другие репозитории ею не управляются. Их фактические настройки не проверялись.
- GitHub может повторно запустить старый workflow с исходной ревизией и прежними
  правилами. Уже запущенные задания также не приобретают новую блокировку.
- Между последней проверкой GitHub API и вызовом Cloudflare остаётся
  неатомарный интервал. Внешний push в него может сделать выпуск устаревшим; полная
  гарантия требует единого контролируемого пути записи и развёртывания.
- Фактическое завершение и распространение deployment Cloudflare в рамках этой
  локальной проверки не подтверждались. После завершения job блокировка GitHub
  освобождается; внешние процессы Cloudflare она не контролирует.
- Если `main` меняется после push созданного коммита, но до проверки, коммит
  остаётся в Git, а сайт не обновляется. Автоматически повторять выпуск нельзя:
  владелец должен проверить текущую `main` и отдельно разрешить развёртывание
  актуального SHA через утверждённый процесс.
- При недоступности GitHub API, отсутствии права чтения или превышении лимита
  проверка также закрывает публикацию. Если собственный коммит уже отправлен,
  потребуется отдельное согласование восстановления.
- Исторический push-сценарий `import-public-domain.yml` по-прежнему требует
  ровно десять новых файлов произведений. При повторном импорте уже имеющихся
  произведений он остановится до push и deployment. Проверка сохранена без
  ослабления; исправление отдельного CI workflow находится в PR #124.

## Следующий PR: Supabase и подтверждение выпуска

Сейчас `publish-approved.mjs` после Git push переводит задания в `published`,
не ожидая Cloudflare. В этом изменении поведение Supabase намеренно не меняется.
Для следующего PR требуется согласовать отдельный протокол:

1. Надёжно сохранять связь задания, проверенных прав, Git SHA и состояния выпуска;
   различать подготовленный коммит, развёртывание и реально опубликованную главу.
2. Переводить запись в `published` только после подтверждения успешного production
   deployment и проверки, что опубликована именно нужная ревизия. Определить
   проверяемый идентификатор deployment и маркер ревизии в сборке.
3. Обеспечить идемпотентность и восстановление после сбоев между Git, Cloudflare,
   обновлением статуса и записью события; повтор не должен заново публиковать текст.
4. Повторно проверять права перед выпуском и предусмотреть отзыв и снятие уже
   опубликованных статических страниц. Полной атомарности между сервисами нет.

Миграции, изменение данных Supabase и запуск такого процесса требуют отдельного
задания и проверки на изолированной среде.
